# Design

## Context

See proposal.md for motivation. Current state:

- Backend: Go + chi, HTTP layer generated by oapi-codegen (strict server) from `backend/api/openapi.yaml`; only `GET /healthz` exists. `config.Supabase` already carries `URL` and `JWKSURL`.
- Supabase: anonymous sign-ins are enabled in `supabase/config.toml` (30 per hour per IP).
- Frontend: bare Nuxt 4 + Nuxt UI app with one placeholder page. Per `frontend/AGENTS.md`, Supabase is used only for authentication, session state goes in Pinia, and backend data goes through TanStack Query.
- The OpenSpec rule files mention `backend/api/http/openapi.yaml`, but the contract actually lives at `backend/api/openapi.yaml` (`api/http/` holds only `oapi-codegen.yaml`). The tasks use the real path.

## Goals / Non-Goals

**Goals:**
- A neighbor reaches the app as a guest in one tap, and keeps the same identity on return.
- The API can trust the caller identity from the Supabase JWT, anonymous or not.
- Supabase owns sign-in, sign-up and token refresh; the API only validates.

**Non-Goals:**
- Auth endpoints in our API for login, register or refresh (Supabase does those), real login, sign-up, or linking an anonymous user to an account (the user id is preserved later by Supabase's identity linking; nothing here blocks that).
- Roles and authorization rules beyond "has a valid session".
- Any other app section (navigation bars, Inicio content).

## Decisions

### 1. The device session is the single source of "already chose"
Supabase's client persists the session in browser storage and refreshes it. The route guard sends a neighbor to the welcome screen only when there is no session; with a session it enters directly. No separate "chose guest" flag is stored. Since guest is the only working option today, a session is equivalent to "an option was chosen". When login ships, this stays correct because logging in also produces a session.
*Alternative:* a separate localStorage flag. Rejected: it can drift from the real session (flag set, session gone) and adds state to keep in sync.

### 2. Frontend runs as an SPA (`ssr: false`)
The session lives in the browser, so server rendering would always render the welcome screen and then flicker. Disabling SSR avoids a server/client mismatch for this first iteration. *Alternative:* SSR with cookie-based Supabase sessions (`@nuxtjs/supabase`). Rejected: more moving parts, and the frontend rule is to use Supabase only for auth, not its Nuxt module's data features. Revisit if SEO or SSR is needed.

### 3. Frontend structure
- `app/composables/useSupabase.ts` (shared client from `runtimeConfig.public.supabaseUrl` / `supabaseAnonKey`) and `app/stores/session.ts` (Pinia: session, `initialize()`, `signInAsGuest()`).
- `app/middleware/auth.global.ts`: awaits `initialize()` once; no session and not on `/welcome` → redirect to `/welcome`; session and on `/welcome` → redirect to `/`.
- `app/pages/welcome.vue`: Nuxt UI card with the two buttons. «Ya tengo una cuenta» shows a `useToast` «Próximamente»; «Comenzar» calls `signInAnonymously()` and navigates to `/`; on error it shows an error alert with a retry.
- `app/pages/index.vue` calls `GET /me` through a TanStack Query query with the access token as bearer, to prove the end-to-end session (replaces the placeholder text). A small API composable adds the `Authorization` header. Token refresh is handled by supabase-js (`autoRefreshToken`), so the frontend never refreshes by hand.
- Layout and copy follow the Figma "Sin cuenta" welcome frame; the implementer asks for the frame link before building the UI (daily Figma call limit).

### 4. API: JWT verification with the project's JWKS
New package `internal/platform/auth`:
- Verifies the bearer token's signature against `SUPABASE_JWKSURL` (cached key set), and checks `exp`, `iss == SUPABASE_URL + "/auth/v1"`, and `aud == "authenticated"`. Anonymous Supabase users use the same issuer, audience and `authenticated` role.
- Extracts `sub` (user id) and `is_anonymous` into a `Principal` stored in the request context.
- Libraries: `github.com/golang-jwt/jwt/v5` plus `github.com/MicahParks/keyfunc/v3` for JWKS fetching and caching.
*Alternative:* call Supabase `GET /auth/v1/user` per request. Rejected: adds a network round-trip to every request. *Alternative:* shared HS256 secret. Rejected: the backend config already uses JWKS, and asymmetric keys avoid distributing the secret.

### 5. Marking protected endpoints in the contract
`openapi.yaml` gets `components.securitySchemes.bearerAuth` (HTTP bearer, JWT) and a global `security: [bearerAuth: []]`; `/healthz` overrides with `security: []`. The installed oapi-codegen does not emit per-operation scope markers, so the server reads the embedded spec at startup, collects the operations with empty `security`, and a strict-handler middleware enforces auth on every other operation. The contract stays the source of truth, no route list is duplicated in Go, and a new operation is protected by default.

### 6. `GET /me`
Returns `200 {"id": "<uuid>", "isAnonymous": bool}`; `401` with a short body otherwise. It is a thin read of the `Principal`, with no database access. It is the only identity endpoint: sign-in, sign-up and refresh go straight from supabase-js to Supabase Auth. It gives PV-47 and PV-49 a real endpoint to verify against.

### 7. Configuration
Backend: `SUPABASE_URL` and `SUPABASE_JWKSURL` become required when the API starts serving authenticated routes (validated in `config.validate`; tests use a fake JWKS). Frontend: `NUXT_PUBLIC_SUPABASE_URL`, `NUXT_PUBLIC_SUPABASE_ANON_KEY` and `NUXT_PUBLIC_API_BASE_URL` documented in `frontend/.env.example` with local-stack sample values.

### 8. Anonymous identity survives refresh
Supabase identifies a session's user by the token `sub`, which does not change on refresh. To keep it that way, `[auth.sessions]` in `supabase/config.toml` must keep `timebox` and `inactivity_timeout` unset, and the same must hold for the hosted Supabase project (to be checked at deploy time, since local config does not govern it). Anonymous users have no credentials, so a lost device session cannot be recovered; creating an account (later story) keeps the same user id.

## Risks / Trade-offs

- [Anonymous sign-in rate limit of 30/hour/IP could block shared networks] → acceptable for the MVP; surface the failure with the retry message (spec scenario) and revisit the limit in `supabase/config.toml` if it shows up in testing.
- [Clearing browser data loses the anonymous identity and its future reports] → inherent to anonymous sessions; account creation (later story) is the recovery path.
- [Anonymous users can accumulate in Supabase] → out of scope; cleanup policy to be decided with the reporting stories.
- [JWKS endpoint unreachable at startup or rotation] → keyfunc caches and refreshes in the background; requests fail closed with 401 if no key can be resolved.
- [SPA mode gives up SSR] → Decision 2; reversible.
